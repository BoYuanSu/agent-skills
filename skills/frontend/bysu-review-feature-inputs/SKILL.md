# 確認功能輸入素材

## 目標

建立 `specs/{FeatureName}/input-review.md`，保留本次功能的素材判讀與決策紀錄。原始素材放在同一功能的 `sources/ui/`、`sources/requirements/`、`sources/api/`。

## 執行方式

1. 確認功能名稱、包含的畫面及不包含的範圍；`{FeatureName}` 使用 PascalCase。
2. 逐一讀取可用的 UI、需求與 API 素材，記錄來源。不得僅依檔名推測內容。
3. 交叉檢查：
   - 畫面欄位是否能從 API 或前端已知資料取得。
   - 需求中的操作是否在畫面上有入口及結果呈現。
   - API 的狀態、錯誤與權限是否能對應畫面狀態。
   - UI 顯示的篩選、排序、分頁或送出資料是否有明確規則。
4. 將問題分為缺口、衝突與待決策事項，說明它影響的畫面、互動或後續合約。
5. 區分阻斷與非阻斷問題。會改變元件結構、主要互動、資料來源或公開合約者為阻斷問題，不自行假設答案。

## 產出內容

`input-review.md` 至少包含：

- 功能與畫面範圍。
- 已檢查的素材清單。
- 已確認的互動範圍。
- 缺口、衝突與待釐清事項，以及各自影響。
- 已確認決策與仍在使用的明示假設。

可用表格或條列呈現。只記錄本次判讀，不複製整份原始素材，也不提前設計元件、資料流或 Adapter。

## 完成條件

- 每項範圍與結論都能追溯到素材或明確決策。
- 阻斷問題已取得決策；否則清楚列出並停在本階段。
- 後續可據此分別建立 Component Hierarchy 與 BDD use cases。
